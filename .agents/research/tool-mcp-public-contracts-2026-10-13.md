# Tool/MCP filtering: installed Pi 1.1.0 evidence

Research date: 2026-10-13. Repository inspected at `ce8b97aafcf640babd40c618070a089a191a534a`. This report is research, not implemented behavior. No tests, inference, installs, network requests, commits or pushes were run. Only this authorized evidence file was written.

## Answer

Public Pi 1.1.0 supports additive changes to **declared tools** via `pi.setActiveTools`, and execution-policy blocking via `tool_call`. It does **not** expose a public filter for codemode discovery, a comprehensive configured-MCP inventory, or enable/disable control over file-configured MCP servers. Therefore a truthful implementation can select tool declarations, select whole connected MCP namespaces as atomic units, and block excluded tool calls. It cannot claim hidden tools disappear from `ALL_TOOLS`/`searchTools`, nor claim MCP servers are disconnected, nor claim a security boundary. Full visibility filtering needs a new upstream host contract.

The public metadata needed for safe identity classification already exists: `ToolInfo.sourceInfo`, `exposure`, and `namespace`. Beware: tools supplied by Pi's built-in MCP manager have builtin extension provenance, but are external MCP tools—not protected internal tools.

## Verified public contracts and limitations

### Inventory and identity

- `pi.getAllTools()` reports name, description, parameters, prompt guidelines, exposure, namespace, annotations, and **sourceInfo** (`SDK/dist/core/extensions/types.d.ts:1553-1559`; implementation `agent-session.js:1078-1089`). It is a registered-tool inventory, not merely currently declared names. Snapshot it anew at every allowed boundary; otherwise tools initially removed from active declarations are lost to future decisions.
- `SourceInfo` contains path, source, scope (`user|project|temporary`), origin (`package|top-level`), optional baseDir. Builtin paths use `builtin:` (`SDK/dist/core/source-info.d.ts:2-27`). Pi assigns base tool definitions paths `builtin:<name>` and SDK custom tools `<sdk:<name>>`; extension tools retain extension provenance (`agent-session.js:2814-2861`). Names alone cannot distinguish a replacement `read` from the real builtin reader.
- Builtin MCP registers tools with namespace `mcp__<normalized-server>`, namespace description from configured description, and namespace instructions from server instructions (`SDK/dist/extensions/mcp/index.js:285-318`). They are owned by the manager extension, not the npm executable behind an MCP server. Classify MCP namespaces before deciding which builtin provenance is protected. Do not automatically protect all `sourceInfo.source === 'builtin'` tools: that includes the MCP manager's tools.
- Namespace normalization replaces `-` with `_` (`SDK/dist/core/mcp-servers.js:50-52`). Use public namespace keys as canonical grouping/allowlist IDs. Do not reverse-guess an original server name or npm package from that key; aliases/config spelling may differ. Tool name collisions get hash suffixes (`SDK/dist/extensions/mcp/index.js:295-307`; `PI/docs/mcp.md:61-69`). Namespace grouping is safer than parsing all tool names.
- `getMcpServers()` means **every server registered by extensions**, not configured file servers (`SDK/dist/core/extensions/types.d.ts:1350-1368`). Configs may contain credentials/URLs/env/headers and should not enter decision payloads. There is no public full inventory for disconnected, disabled, empty, or resource-only servers. `mcp_servers_change` is extension registration changes, not connected inventory changes (`types.d.ts:550-560`).
- Pi packages and MCP servers are different concepts (`PI/docs/packages.md:1-6,119-129`; `PI/docs/mcp.md:24-69`). SourceInfo can identify an extension package, but builtin MCP tool provenance does not disclose the server executable's package. Label the mode **MCP servers/namespaces**, with any “package” wording explicitly defined, not npm-package grouping.

### Active declarations and indirect reachability

- `getActiveTools` is the currently declared set. `setActiveTools` ignores unknown/hidden names; codemode/deferred remain callable whether active or not (`SDK/dist/core/extensions/types.d.ts:1257-1267`). Direct tools are callable only while active; model-only tools are never nested-callable (`types.d.ts:382-394`; `agent-session.js:1143-1149`).
- Tool exposure definitions and `prepareLoadout` are public (`PI/docs/extensions.md:174-211`). `prepareLoadout.hiddenDeclarations` hides declarations but keeps tools active/callable; it cannot remove tools from registered/callable inventories. Re-registering another extension's MCP definitions as hidden is ownership-invasive and loses execution behavior; do not do it.
- Codemode discovery includes every callable tool, with names/descriptions; `describeTool` adds parameter declarations and guidelines, `describeNamespace` adds instructions (`PI/docs/codemode.md:29-76`). A tool-call block prevents use, not discovery. `tool_search` can reactivate excluded deferred tools (`PI/docs/mcp.md:199-234`). A subsequent execution gate must remain authoritative; declarations alone are not enforcement.
- MCP docs expressly state inactive indirect tools remain reachable across tree/resume/fork (`PI/docs/mcp.md:220-223`). Keeping internal `codemode`/`tool_search` always allowed necessarily leaves these indirect discovery mechanisms operational.
- `tool_call` can block both direct and nested executions; MCP calls pass the same pipeline and nested calls carry `parentToolCallId` (`PI/docs/mcp.md:247-253`; `PI/docs/extensions.md:149-162`). This provides relevance execution gating, not an OS/network security boundary: allowed `bash` can reach the same resources independently (`PI/docs/security.md:1-31`).

### Timing and late inventory

- Pi records initial prompt/tools as a system message, then appends tool/prompt deltas before the next request (`PI/docs/extensions.md:213-219`; `PI/docs/sdk.md:29-36`; `PI/docs/session-format.md:77-88`). Public `setActiveTools` can therefore implement progressive additions without custom skill-style advertisement messages.
- `before_agent_start` exposes structured selectedTools. Explicit selectedTools changes win over a simultaneous live `setActiveTools` change; when not explicitly edited, the live set wins (`SDK/dist/core/agent-session.js:1590-1598`). Pick one authoritative application path. A test should deliberately combine an earlier selectedTools edit with our setActiveTools to expose the conflict.
- Between turns, Pi refreshes selectedTools from the current live active set before the next request (`agent-session.js:535-563`). Calling public setActiveTools at `turn_end` affects that next request; do not retain `_runSystemPromptOptions`, patch provider payloads, or force continuation.
- Direct/model-only tools are auto-activated upon late registration; refresh adds newly declarable tools (`agent-session.js:2874-2889`; public intent `PI/docs/extensions.md:193-196`). There is no public tools-changed lifecycle event. A strict “never declare an unscored late tool” guarantee requires reconciliation before each request, not only at initial picking. `turn_start` and normal picker boundaries can reconcile using `getAllTools`; arbitrary concurrent registration between reconciliation and provider request remains a host-level race.
- MCP servers connect asynchronously; first prompt waits up to ten seconds only for direct-exposure servers, while discovery/search calls wait for named/all servers (`PI/docs/mcp.md:95-100`; implementation `mcp/index.js:1010-1070`). Tools connected after an early user's decision handler may be auto-declared later in the same before_agent_start dispatch. Test late builtin MCP handler registration explicitly, not only already-loaded inline tools.
- Builtin MCP writes `event.systemPromptOptions.sections.mcp_servers` every prompt (`mcp/index.js:1032-1041`). Files load separately from builtins, but final order follows extensionPaths; inline factories append last (`SDK/dist/core/resource-loader.js:523-574`), and builtin resources are normally appended after discovered resources (`package-manager.js:725-745`). Hence ordinary early user extensions cannot reliably prune this section. Registering another handler at session_start does not globally move its owning extension after builtin MCP. Do not rely on parsing section text or handler-registration timing as a public ordering contract.

### Branches, resumes, compaction, and ledgers

- `session_start` covers startup/reload/new/resume/fork (`SDK/dist/core/extensions/types.d.ts:562-570`). `session_tree` reports the new leaf (`types.d.ts:650-657`). Reconstruct selection/initial-pick records from `ctx.sessionManager.getBranch()`, not all file entries (`PI/docs/extensions.md:244-258`).
- Pi itself restores declarations from replayed system tool patches when starting/resuming and after tree navigation (`SDK/dist/core/agent-session.js:1368-1377,3339-3353`). A global session-memory allowed set would leak selections across branches.
- Compaction stores the full system/tool checkpoint; unlike skill custom messages, native tool declarations need no custom re-delivery (`PI/docs/session-format.md:131-156,249-265`). Non-context custom entries can still hold branch policy/initial-picked markers using public appendEntry or boundary custom drafts (`PI/docs/extensions.md:244-257`). Define whether disabled filtering records full baseline or simply leaves Pi untouched; this user asks enable-later filtering, so do not automatically inherit the skill policy's irrevocable full-advertisement rule without deciding it.
- `turn_end` receives pending user messages through its boundary preview and supports appended custom drafts (`SDK/dist/core/extensions/types.d.ts:760-813`). Never overwrite prior drafts; return entries with earlier entries preserved. Cancellation and generation changes must guard all application and persistence after awaits.

### Shared MCP resource tools

`list_mcp_resources`, `list_mcp_resource_templates`, and `read_mcp_resource` are manager tools spanning servers, without per-server namespaces. Their source is still builtin MCP. Effective exposure is the widest exposure among enabled non-hidden resource servers (`SDK/dist/extensions/mcp/index.js:357-380`; `PI/docs/mcp.md:236-245`). Server-less list calls enumerate all such servers (`SDK/dist/extensions/mcp/resources.js:164-195`); read calls require `server` (`resources.js:225-240`). Whole-MCP execution gating requires an explicit local resource policy. To avoid inspecting arguments at all, conservatively block shared resource tools whenever a subset of servers is excluded; this sacrifices useful allowed-server reads. To selectively permit reads/listing, local inspection of `event.input.server` is required but need never enter the decision payload. Server-less listing cannot be selectively filtered with a tool_call block; require an explicit server or block. Resource-only servers cannot be comprehensively selected from getAllTools namespace inventory.

## Existing repository integration points (observed)

- Host type currently only includes on/registerCommand/appendEntry/getActiveTools; extending public required/optional host methods and fakes is necessary (`src/extension/contracts.ts:14-15`).
- Settings currently only have global enabled/backend/global skill allowlist/relevance. Relevance defaults enabled, threshold 0.375, cap 12, prompt cadence; these must not imply tool filtering enabled (`src/settings.ts:9-41,116-129`). Introduce separate disabled-by-default tool settings and allowlists; clarify whether global enabled is master decisions or skill-only legacy behavior.
- Runtime already owns generation-based cancellation, asynchronous atomic writes, session start/tree/shutdown resets, queued latest-user extraction, and decision-client creation (`src/extension/runtime.ts:26-121,125-164`). Preserve independent caches and failures for tool and skill features. Existing resolveClient checks skill-enabled flags, so cannot directly reuse that gate for separately enabled tools (`runtime.ts:147-158`).
- Existing skill additive scorer/caching is pure and checks abort before cache and before applying results (`src/apps/skill-additions.ts:39-61,64-110`). Its request builder and rubric explicitly describe skills and serialize state.skills (`src/apps/relevance.ts:90-136`); mechanically feeding tools into it would mislabel decisions. Factor a metadata-generic scorer or provide tool/MCP-specific request builders while keeping portable layers free of Pi runtime dependencies.
- Existing latest queued-user handling and canContinue/completed guards are appropriate boundaries (`src/extension/runtime.ts:125-144,285-338`). No assistant output, tool arguments/results should be incorporated as “subtasks”; progressive mode means successive remaining choices for the bounded latest user task.
- Existing real offline Pi harness uses faux provider/in-memory manager/injected decision client and validates commit order, steering, compaction (`test/extension-real-pi-session.test.ts:1-70,72-181`). Extend this approach rather than relying on fake Pi to assert host tool timing. Existing fakes must support getAllTools/setActiveTools if these become required (`test/helpers/pi-sim.ts:79-105`).
- `.agents/plans/mcp-visibility.md` is a superseded plan, not code. Its fail-open default, old minLabel policy, old command names, and assumed absence of source metadata should not be copied. Latest user requirements override these. Existing policy in AGENTS.md disallows tool metadata in decision payloads; user now expressly requests tool/MCP filtering, authorizing bounded names/descriptions for this feature only. Revise guidance to preserve no schemas/args/results/transcript/paths/namespace instructions/server configs.

## Feasible scope and falsifying checks for implementation handoff

These are recommended checks, NOT tests run by this researcher:

1. Separate feature toggles: tool off + skill on makes no tool requests; tool on + skill off still requests tool decisions. Missing backend keeps existing Pi loadout intact only if that is explicit disabled/unconfigured policy, not accidental fail-open.
2. Inventory: builtin base read versus extension replacement read; builtin:mcp namespaced tool is external; hidden is never activated; SDK non-MCP tool is candidate in all-tools mode and untouched in MCP mode; namespace hyphen normalization; missing/unknown source metadata is never fabricated as internal.
3. Atomic MCP mode: a pinned/selected namespace includes all its eligible tools, including late members without per-tool scoring. Individual tool pin must not silently breach server atomicity—either ignored/rejected for that mode or visibly promotes whole namespace by documented policy.
4. Real Pi initial before_agent_start: rejected direct tool absent from provider declarations; accepted tool present. Run selectedTools-conflict test and builtin MCP late-registration test.
5. Real Pi turn_end: next-best tool additions produce native system toolsAdded before next request, with unchanged existing selections; no forced extra model request. Initial-only picks once per branch; new-user-prompt mode handles queued steering/follow-up; progressive mode excludes added units from scoring and caches same-task scores.
6. Late registration: register direct tool after initial prompt and verify pre-request reconciliation; update namespace inventory with added/withdrawn/hidden tools. Selected MCP permits late member; unselected MCP blocks late member even before another scoring round.
7. Counterexample to visibility claims: keep codemode active, register inactive deferred tool, verify it remains in ctx.tools/discovery while direct declaration is absent; tool_call blocks nested execution. tool_search may activate it, so validate reconciliation and block after search.
8. Branch/reload/compaction: two sibling selections never leak; restored unavailable names stay pending only under Pi rules; custom policy ledger survives compaction; native system checkpoint keeps tool selection; no redundant skill-style delta for tools.
9. Privacy sentinel: populate schemas, tool args/results, namespace instructions, path/baseDir/config URL/header with sentinel strings; assert tool/MCP decision requests contain only bounded task and approved metadata. Names/descriptions are third-party untrusted data, not instructions. Diagnostics contain safe codes/counts only.
10. Abort/settings-save races: deferred decision completion after reload/branch/settings save applies nothing. No mutation before final generation/abort guard. Pins bypass threshold/cap/failure and preserve unloaded names across allowlist edits.
11. Resources: explicit disallowed server blocked; unscoped list conservative policy; resource-only server limitation documented. Never silently call resource tools “internal always allowed” while claiming whole-MCP off.
12. Existing full offline suite/typecheck/pack checks remain parent's responsibility. No live inference is necessary to establish host contracts.

## Remaining unknowns / hard blockers

- Full indirect invisibility and disconnected/zero-tool MCP inventory: **hard public-API gap**, established above.
- Literal whole-server disable/disconnect versus relevance execution gating: **hard public-API gap** for file-configured servers. Public unregisterMcpServer only owns this extension's registrations.
- Arbitrary third-party MCP adapters may lack native namespace metadata; no truthful generic server grouping can be promised. Treat unknown adapters explicitly unsupported or tools-only, not silently guessed packages.
- Strict final-loadout reconciliation against concurrent third-party changes: requires integration tests and honest host-race limitation; there is no public tool-selection owner/filter hook.
- The user wording “both modes” for three listed cadence behaviors needs a deliberate naming decision: initial-only, new-prompts-only, progressive tool-round addition. This is a product decision, not a fact about Pi.
