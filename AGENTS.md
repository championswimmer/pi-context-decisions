# Agent guide

`pi-context-decisions` is a Pi extension with four decision backends, one internal `bool`/`choice`/`score` API, and **score-only, additive** skill-advertisement picking. Load it early. **Opt-in (default off) tool/MCP filtering is implemented as relevance gating through public Pi APIs; it is not a sandbox or permission boundary.**

## Layout and status

- `src/extension.ts`: Pi package entry; `src/extension/`: lifecycle, `/decisions` user settings command, host contracts. Register only `decisions`; no compatibility alias.
- `src/settings.ts`: validated, atomic, credential-free user settings plus global always-allowed skill names.
- `src/project-allowlist.ts`: names-only `<cwd>/.pi/pi-context-decisions.json`; `src/apps/allowlist.ts`: pure scope policy.
- `src/extension/skill-ledger.ts`: branch-derived advertisement ledger (base records + hidden delta messages) and the canonical delta builder; `src/apps/skill-additions.ts`: pure additive scoring (`scoreAdditions`, `RelevanceScoreCache`). `src/extension/runtime.ts` wires them into `before_agent_start` and `turn_end`.
- Tool/MCP filtering (separate feature, `settings.tools`, default off): pure `src/apps/tool-inventory.ts` (provenance classification, MCP namespace and extension groups, candidates), `tool-policy.ts` (availability, promotion, reconcile), `tool-additions.ts` (`IncrementalScoreCache`, `scoreToolAdditions`; `relevance.ts` has a `subject` option for tool/MCP request shapes); `src/extension/tool-ledger.ts` (branch ledger `context-decisions-tools` + names-only notice), `tool-filter.ts` (boundaries, `setActiveTools` reconciliation, `tool_call` gate), `queued-task.ts`. The project allowlist file also holds `alwaysAllowedTools`/`alwaysAllowedMcpServers`.
- `src/extension/decisions-history.ts`: read-only `/decisions history` model/report, derived from committed active-branch records and Pi system skills sections; groups before assistant responses, skips empty turns, distinguishes skill advertisements/base/re-delivery, tool availability and notice membership. The history routes share the settings overlay; RPC/print use a bounded names-only report. No new persisted history or live score buffer: added skills and tools carry only numeric `picks` (raw 0–2 score and the stored threshold) inside the existing delta/tool-ledger records, and allowlist grants are marked `allowlisted`/pinned, never with a pick.
- `src/extension/settings-dialog.ts`: the floating `/decisions` dialog (one overlay, internal routes); `settings-model.ts`: pure field/row/layout helpers (no Pi/TUI imports). `src/extension/allowlist-picker.ts`: A-Z/fuzzy and explicit relevance-ranked scoped editor, embedded as a dialog route.
- `src/index.ts`: portable application/core exports.
- `src/decision/`: canonical primitives, validation, client, typed errors.
- `src/core/`: Pi classifier and direct TypeSafe/OpenAI/OpenRouter transports/codecs/auth.
- `src/host/pi-credentials.ts`: opt-in standalone public SDK credential adapter, exported as `./pi-credentials`; active extensions keep using `ctx.modelRegistry`.
- `src/catalog/`: **static checked-in eight survivors of the original top ten** OpenRouter decisions plus pure picker merge. Snapshot 2026-10-12, token window October 5–11. Future updates require code changes, never runtime discovery.
- `src/apps/`: metadata-only relevance and skill policy; public `pickSkills` composes existing ranking/filtering for all four backends. Explicit picks default to no inventory minimum; automatic hook defaults to eight.
- `test/`: offline fixtures and mocked real Pi registration/lifecycle/commands. `test/helpers/settings-ui.ts` changes settings the way users now can (RPC menus: `setSetting`, `setModel`; the real terminal editors: `saveAllowlist`) because no setter subcommands exist. `test/helpers/pi-sim.ts` is an offline stand-in for Pi's branch/compaction/context-edit projection and before_agent_start/turn_end commit order: a contract fake, not a Pi test. `test/extension-real-pi-session.test.ts` drives the REAL `AgentSession` (faux provider, in-memory session, injected decision client; offline) to check Pi's actual commit order, branch contents, context conversion, steering, tool rounds and compaction.
- `.agents/skills/`: project-local skills; `.agents/plans/`: pending implementation handoffs (none pending now); `.agents/research/`: archived research and live-validation evidence.
- `../pi-skill-picker-jev`: pattern reference only; do not copy wholesale or add as a dependency.

Archived research proposed dynamic discovery and fail-open defaults. Latest user requirements override it: **static top-ten snapshot trimmed by confirmed routing failures, and default fail closed**, explicit fail-open optional. Completed and superseded plans have been pruned; keep pending work in `.agents/plans/`. Preserve historical evidence in `.agents/research/`; add a uniquely named follow-up when needed.

## Working rules

- Read installed Pi docs fully and relevant linked declarations before changing host APIs. Current implementation targets `@earendil-works/*` Pi 1.1.0, not legacy namespaces.
- Read callers/tests before editing; name the files, behavior, and falsifying check. Keep changes scoped and preserve concurrent edits.
- Researchers/architects hand off through `.agents/plans/`. Mark proposed work clearly; do not describe plans as implemented.
- Keep dependency direction: apps/core → decision; extension → layers. Pure app/decision/catalog modules must not acquire Pi runtime dependencies.
- Binary aliases belong only at provider codec boundaries; internal applications use `bool`. Do not fabricate optional metadata or cost.
- Credentials for all three direct providers come from public request-time `getProviderAuth` first, then env (`OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `TYPESAFE_API_KEY`). Exact `openai` API key only, never `openai-codex`/current-chat substitution. Reject OpenAI source `OAuth` even when cached snapshots are empty; do not blanket-reject OpenRouter OAuth. Standalone SDK adapter respects Pi defaults (`~/.pi/agent`, overridden by `PI_CODING_AGENT_DIR`) and disables startup model-network refresh. Delegate references/commands to Pi; never read auth files directly, log keys, or persist secrets/settings tokens.
- Skill decision payloads contain the latest bounded USER prompt (or newest queued steering/follow-up user text) and skill name/description metadata only. No bodies, paths/locations, images, transcripts, assistant text, tool names, arguments or results, in every cadence. **Tool/MCP decision payloads (opt-in, user-requested)** add exactly: tool name + bounded description + MCP server or extension label (`tools` mode), or group key + server/extension label + namespace description (MCP only) + bounded tool names (`mcp` mode). Never parameter schemas, annotations, namespace `instructions`, provenance paths, server configs, arguments, results, assistant text or transcripts. The gate reads only the resource tools' local `server` argument and never forwards it. Diagnostics contain only safe codes/counts/usage. Canonical skill locations appear only in the chat-model delta message, as in Pi's own skills section.
- **Fail closed** on active decision/configuration errors: a failed round adds nothing and never removes. Adding every remaining skill requires explicit `failMode: "open"` (never for config errors or aborts). Disabled/unconfigured/below-minimum intentionally makes no calls and keeps every skill advertised; the branch records that (base entry), so later enabling cannot drop a skill the model saw.
- **Skill picking is score-only; the `choice` decision primitive stays for the library/smoke test only.** Settings have one framework-wide normalized `decision.threshold` in [0, 1] (default 0.375), inclusive: a skill qualifies when its 0–2 score is at least `2 × threshold` (exact in IEEE-754). `mode`, `minLabel`, `relatedThreshold` and `directThreshold` exist only as load-time migration inputs (`threshold = (minLabel === "directly_relevant" ? directThreshold : relatedThreshold) / 2`; `mode: "choice"` migrates with one warning; invalid legacy values stay errors; loading never rewrites the file) and as rejected options to the app API. `RelevanceItem` has no label. `chunkSize` (1–50) is the shard size, defaulting to 50 with `concurrency: 0` (all shards parallel); reduce it for a lower declared provider/client `maxQuestions`; evaluate every candidate, not just the first shard. `maxSkills` is the cap on NEWLY added skills per round, ranked globally across shards (never per shard, no session total); pins/manual-only policy and stable references survive.
- **Additive advertisement (these requirements supersede "only mutate `systemPromptOptions.skills`").** Never remove or re-score an advertised skill. Exclude advertised skills BEFORE sharding. `before_agent_start` sets `systemPromptOptions.skills` only to the stable base (pins, or full inventory once filtering was off/unconfigured/below minimum), and returns new skills as an append-only hidden `custom_message` built with the PUBLIC `formatSkillsForPrompt`; `turn_end` returns the same as a `custom_message` entry draft, but Pi's boundary dispatch REPLACES accumulated drafts with what a handler returns, so always return `[...event.entries, ours]`. Check cancellation immediately before returning (cached scores must not bypass it), clear branch-transient state on `session_tree`, and record no base without a `read`/`bash` reader (Pi renders no skills section then). Never set `continue`, use `context`/`context_with_system`, edit provider payloads, or retain Pi's private run options. The ledger is derived from `ctx.sessionManager.getBranch()`/`buildSessionProjection()` and exists only once Pi committed the message; compaction/context edits that hide a delta cause re-delivery (no scoring). Delta messages are user-role context, not a native system delta; say so. `cadence: "prompt"` (default) also handles queued steering/follow-up user text at `turn_end`; `"tool-round"` runs only after completed tool results (never aborted/errored/assistant-only/final turns), reuses cached scores for the same task, and is progressive addition, not subtask inference. Add no cadence that needs tool or assistant data without explicit user approval.
- `/decisions` opens three peer tabs: **Skills** (`main`: immediate `relevance.enabled` toggle, skill cadence, both skill allowlists, Status, Close), **Tools** (`tools`: independent `tools.enabled` toggle, mode, tool cadence and four allowlist editors), **Advanced** (`advanced`: shared provider/execution and model, then relevance threshold, shard size, Skills · Max added per round, On failure, Timeout, Concurrency, Skills · Minimum inventory, prompt/description size limits, Tools · Max added per round, Tools · Minimum candidates). No nested Advanced… row or master switch. Shared `decision.*` owns threshold/failMode/timeoutMs/chunkSize/concurrency/maxPromptChars/maxDescriptionChars; both pipelines, lazy tool decisions and explicit allowlist ranking read it (ranking sorts only). Skill/tool caps and minimum inventory gates stay distinct policy: tools can be entire groups; preserve defaults skills 12/8 vs tools 8/0. Legacy `relevance.*` tuning and tools threshold/failMode/description migrate on load with one warning, never a rewrite; explicit `decision.*` wins per field, conflicting legacy policies use higher threshold / shorter description / closed if either was closed; validate even shadowed old values. Old master `enabled: false` migrates both switches off, and the next save drops it and all old tuning fields. The tool editor stays NESTED: locked built-ins first, then collapsible MCP-server and extension groups with `[ ]`/`[-]`/`[x]` headers, then ungrouped tools; header Space pins the group key, child saves its tool name, one save writes both lists, unloaded names/keys remain stable rows even on deselect; MCP editor is the same group list, flat. In the terminal it is ONE floating `ctx.ui.custom(..., { overlay: true, overlayOptions: SETTINGS_OVERLAY_OPTIONS })` dialog hosting an internal route stack (main/tools/advanced/provider/model/edit/options/status/allowlist/history/history-batch). The three tab roots are `main`, `tools`, `advanced`: Tab/→ cycle forward and Shift+Tab/← backward with wraparound, replacing the single root frame only at stack depth 1 (never from edit/options/allowlist/etc.); Esc on any root closes; sub-routes return to their originating tab. Tool/MCP allowlists deep-link under Tools, provider/model under Advanced, skill allowlists/history under Skills. Never add a tab by pushing a second overlay. Never call nested `ctx.ui.select`/`input`/`custom` from it: Pi's `done` removes the TOPMOST overlay, so stacked overlays can close the wrong one; close only through the saved `done`, exactly once, never `OverlayHandle.hide()`. RPC keeps select/input menus with the same grouping (no tabs: Skills / Tools / Advanced sub-menus; the allowlist editors are terminal-only). **The dialog is the only place settings change: do not add `/decisions` setter subcommands** (the user removed them to keep the command surface small). The only arguments are `status`, read-only `history`, `test` (explicit paid call), read-only `tools list`/`mcp list`, and `pin`/`unpin` (legacy `pinned`, deliberately not in the dialog). Print/JSON mode prints the status; settings there are file edits plus `/reload`. Anything a dialog row can do must not get a text command; `test` and the inventory list reports are the only things the settings rows cannot; the read-only `history` argument deep-links to history routes inside the same overlay. Provider/model availability uses public request-time Pi credential resolution, not chat-model inventory guesses; label missing keys and guide to the matching env variable or `/login <provider>`. Reject unusable selections before atomic persistence; never enable filtering as a side effect of selecting a provider/model.
- Scoped allowlists mean **always included**, not restrict-to-only: for skills AND tools/MCPs/extensions, global matches public `sourceInfo.scope` user/temporary/missing, project matches project scope only. Tool/MCP editors retain provenance scope (never relabel all items to the edited list); nested groups and flat group candidates are scoped too. Global lists save to `<getAgentDir()>/pi-context-decisions/settings.json`, project lists to `<cwd>/.pi/pi-context-decisions.json`. Pi 1.1.0 `ToolNamespace` has no server config origin and built-in MCP tools all carry `builtin:mcp` / temporary scope, so even project-configured built-in MCP servers currently follow Global: state the limitation in docs/editor/status, never read `mcp.json` or private runtime to guess. Unobservable/resource-only groups follow missing-scope semantics (global only). A group inherits its members' common scope; mixed-origin groups cannot be allowlisted as a whole and are omitted as loaded group-editor candidates, with scoped individual tools still selectable. Individual pins/ledger tools never promote a mixed-origin group; relevance and existing whole-group ledger grants remain additive. Effective pins bypass scoring/threshold/cap and survive fail-closed. Persist names only; project files are bounded, regular-file-only reads and atomic writes. Malformed project lists warn and become empty, never full inventory.
- `/decisions` settings expose both allowlist editors. A-Z search is local; typing/tabs make no calls. Only explicit Ctrl+R/search Enter ranks the query with configured decisions (`rubric: "topic"`, configured shared decision batching/concurrency/deadline/metadata limits); no model/key gives inline setup guidance. Cancel old/closed ranking, reject stale completions, show stale query state. Save only on explicit Ctrl+S; preserve unloaded names. The editors are terminal-only (RPC says so; print/JSON edit the files and `/reload`); never call custom overlays outside `mode === "tui"`.
- Keep terminal text sanitized and visible-width bounded; propagate focus to Input for IME. Mocked key/render tests are not a visual terminal pass.
- Dialog lifetime and context: dialog work uses a dialog-owned `AbortSignal`, never `ctx.signal` (that is the agent-run signal) and never a spread `{...ctx}`; use `scopedContext`, whose `ui`/`modelRegistry` getters throw once the dialog is closed (Pi invalidates every ctx property after reload). `registerCommands` returns `closeDialogs()`, called FIRST and synchronously in `session_shutdown` (and at `session_start`), because Pi removes a custom overlay on reload without resolving it. The dialog is NOT in `pending`: settings saves abort in-flight decisions, never the dialog. The dialog must render within `dialogHeightBudget(rows)`, because Pi slices overlay output at `maxHeight`; percent sizes are re-resolved per render, option functions are not. No optimistic state: show values from `ops.snapshot()`, refreshed after each successful save and on route entry, never per render. Dialog errors render inline, not as transcript notifications.
- While the dialog has focus the session keeps streaming underneath, but Esc/Ctrl+C act on the dialog, not the agent. A key that hands typing back while the dialog stays open is deliberately not implemented.
- **Tool/MCP filtering rules.** Opt-in, `tools.enabled` default false, independent of `relevance.enabled`; off means no `getAllTools`/`setActiveTools` calls, no entries, no extra status writes, every call passes. Two modes: `tools` (each external tool) and `mcp` (group mode: whole groups, where a group is an MCP namespace OR an extension, handled identically; allowlisting or already having ANY tool of a homogeneous-scope group promotes the whole group; mixed-origin groups keep individual grants scoped). **This supersedes the old rule "other extension tools are never filtered" in `mcp` mode**: only extension tools with no usable provenance (no group) pass there. **Internal = Pi-assigned provenance only** (`sourceInfo.source === "builtin"` with a `builtin:` path and no `mcp__` namespace); the MCP namespace check runs FIRST because built-in MCP provenance belongs to external server tools. Never classify by name, `reachesTools` or core-name lists; SDK/extension/unknown-provenance tools are external. Group MCP tools only by Pi's public `namespace.name` (`mcp__<server>`) and extension tools only by Pi's public `sourceInfo` (`extensionFullName`: package `source` (never `.`/`..`), else the RESOLVED `baseDir`; else the synthetic `<kind:name>` path; else the file/dir name; display label = first 48 chars; key = `ext__<name>` within 64 chars from the FULL name: canonical-up-to-case-and-`-` names as is, any other name `ext__<ascii slug>_<10-hex sha256 of the NFC name>`, empty slug `ext__ext_<hash>`; same-named extensions merge, no usable name = ungrouped); never parse tool names, read `mcp.json`, read extension files or guess packages. Group allowlist entries are `[A-Za-z0-9_-]{1,64}` or `mcp__`/`ext__` + such a name (the canonical prefix is IN ADDITION to the 64-char bound, in settings, project file, commands and editors). An `mcp__` allowlist entry is exclusively a canonical MCP namespace key and an `ext__` entry exclusively a canonical (lowercase) extension key, both kept in the existing `alwaysAllowedMcpServers` list (a raw server named `ext__x` is `mcp__ext__x`). Extension labels are derived names, never paths, and are the only provenance-derived text that reaches the decision model. MCP resource tools are internal but gated by their `server` argument (unknown/resource-only servers fail closed unless globally allowlisted); this is a documented routing policy, not an exception to "internal always allowed". Availability is additive per branch (ledger entries `context-decisions-tools`; the first active boundary on a fresh branch always writes a marker so a late tool is never mistaken for mid-session enabling; enabling mid-session records existing tools as seen, a documented limitation; disabling restores only tools we withheld). Cadences `initial` (first user prompt only; `considered` is persisted so catch-up/reload never re-picks; custom-message runs never supply the task; a failed pick retries), `prompt`, `tool-round`. Only use `pi.setActiveTools` (restore only what we withheld); never edit `selectedTools`, never use `context_with_system`, never prune `sections.mcp_servers`. Calls to unavailable external tools are blocked in `tool_call` (covers codemode/nested); an unscored candidate gets one single-flight lazy decision. Fail closed on config/decision errors; settings errors keep enforcing an existing ledger. Gate policy when the registry cannot be read: use the last classified snapshot (internal pass, known external per ledger/allowlists, unknown blocked; no snapshot blocks all); an unreadable branch is never mid-session evidence (gate only, no writes); stale generations (settings/allowlist save, disable, mode change, branch change) mutate nothing, while a merely cancelled run reconciles from committed state only. Unscoped resource listing is always blocked while filtering is on; resource-only allowlist keys are recorded canonically (`canonicalServerKey`: a `mcp__` prefix is exclusively a namespace key). Unconfigured/below-minimum applies at every boundary and the gate; disabling restores at `turn_end` too. Ledger records are chunked (1000 names per list), never truncated. The notice speaks only about indirect candidates (groups are named by canonical key: `MCP servers: mcp__x`, `extensions: ext__y`). Say plainly in docs/status that it is not a sandbox and discovery (`searchTools`, `tool_search`, `mcp_servers` section) and server connections are unaffected. Skill and tool decision passes run concurrently (the tool `before_agent_start` handler is registered first and starts the skill pass). Tests: `test/extension-tool-filter.test.ts` (sim host), `test/extension-tool-commands.test.ts`, `test/extension-real-pi-tools.test.ts` (REAL `AgentSession`).
- Later extensions may overwrite the base skills array, and nothing can retract a delta already in context. Never claim tool/MCP filtering is access control.
- Keep native OpenRouter entries constrained to the same static retained list; do not destructively override Pi's provider. Missing native registrations stay errors, not automatic direct-backend fallback.

## Verification and publishing

```bash
npm ci --ignore-scripts
npm test
npm run typecheck
npm pack --dry-run --ignore-scripts
```

Every behavior change needs focused tests and the full offline suite. `test/extension-settings-overlay-render.test.ts` drives Pi's real `TuiMainScreen` into `@xterm/headless` (dev dependency, pinned to the version pi-tui tests with): a renderer test, not a visual terminal pass. An optional manual pass is possible in tmux with an isolated `PI_CODING_AGENT_DIR=$(mktemp -d)`, `--offline --no-session -ne -e ./src/extension.ts` and a `!` bash loop for background output; choose "Do not trust (this session only)" at the trust prompt and delete the temp dir afterwards. Local dev dependencies and lockfile make typecheck reproducible; no sibling tooling is required. Default checks must not make inference calls. Report commands actually run, failure modes, and unverified paths. A mocked UI is not a visual terminal check.

Live smoke validation on 2026-10-12 retained eight OpenRouter models after two confirmed guardrail restrictions; do not replenish the static list automatically. Direct Luna also passed all three primitives using Pi's stored `openai` API key with the env key absent. `scripts/live-smoke.ts` requires explicit `PI_CONTEXT_DECISIONS_LIVE=1` and may incur charges; explicit `gpt-6-luna`/`openai`/`luna` selects only Luna, while the no-argument default excludes it. Smoke credentials are SDK Pi-first/env-second. Default checks remain offline.

Releases: tag-driven via `.github/workflows/release.yml` (npm trusted publishing, no `NPM_TOKEN`); follow `.agents/skills/release/SKILL.md`. Never `npm publish`, tag, or push a tag without explicit user authorization for that release. `0.1.0` is published manually once by the user; keep `package.json` and `package-lock.json` versions in sync.

Do not install, commit, push, or touch network unless authorized. The designated sole Git publisher handles tested milestones; inspect staged content for secrets, never force-push, and leave unrelated work untouched.
